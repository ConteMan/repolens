# ADR-007: 仓库可选约定的准入条件

- 状态：提议
- 日期：2026-08-19

## 背景

repolens 的第一价值主张是"零配置、仓库原样渲染"：仓库不必为工具而组织。但部分阅读体验（术语标注与解释、名词表、其他结构化标记）无法从仓库现有内容推断出来，只能由作者显式提供额外信息。

这类需求与定位表面冲突，且会反复出现。缺少一条成文边界时有两种滑坡：一是逐个特性重新辩论，结论不一致；二是逐步累积"必须这么写才好看"的要求，最终变成 MkDocs / Docusaurus 式的"仓库为工具而组织"，价值主张失效。

同时存在一条看似省事的替代路径：由 repolens 扫描正文，按内置或外部词表自动识别术语并加注。它绕开了"要求仓库配合"的问题，但引入了别的代价，需要一并裁决。

## 决策

1. repolens 可以定义**仓库可选约定**（opt-in repository convention）：一组仓库自愿采用、采用后获得额外渲染能力的书写形式与数据格式。此类约定必须同时满足三条准入条件：
   - **未采用零影响**：仓库不含该约定时，构建过程与输出产物与不存在该特性时完全一致，不产生额外文件、告警或性能开销；
   - **采用后不破坏别处**：约定的书写形式在 GitHub、通用 Markdown 渲染器与纯文本阅读下仍是合法、可读的内容，不产生渲染错误或不可理解的残留标记。仓库不因采用约定而在 repolens 之外劣化；
   - **显式激活**：约定由仓库内可见的文件、目录或标记显式触发，不依赖对正文语义的启发式推断。
2. **不对正文做启发式自动标注**。repolens 不扫描正文自动识别术语（或其他语义对象）并改变渲染结果。此类分析若要提供，只能是面向人的建议输出（独立命令的报告），不得进入浏览层渲染。
3. 仓库可选约定属于配置的渲染信任域（ADR-005）：仓库内可以完整定义，但不得影响拉取来源、输出位置与访问控制。

## 理由

- 三条准入条件把"仓库可以为工具组织"与"仓库必须为工具组织"分开。`.repolens.yml` 早已是同一性质的存在——不写照常工作、写了能定制——本 ADR 只是把这条隐含规则显式化并加上第二条约束（不得让仓库在别处劣化），后者是 repolens 特有的、比一般站点生成器更强的要求；
- 否掉启发式自动标注的理由：
  - **不可预测**：同一个词在不同语境含义不同，误标率不可控，而作者没有可靠的 opt-out 表达手段；
  - **两层输出漂移**：镜像层是逐字节原文，浏览层却出现作者没有写的内容，违背 ADR-001 中"浏览层是原文的视图"这一前提；
  - **不可复现**：词表变化会让历史版本的渲染结果随之改变，与"构建结果只由 repo + ref 决定"冲突；
- 保留"建议输出"这条出口，使自动分析的价值仍可获得，但由人决定是否写入仓库，决定权和可复现性都留在作者手里。

## 后果

- 新增此类特性时，spec 必须逐条论证三个准入条件如何满足，其中"采用后不破坏别处"通常要求约定复用 Markdown 既有语法承载（如链接、脚注），而非发明新的行内标记；
- 特性默认关闭，且"关闭"必须是干净的：关闭状态下遇到该约定的标记时给出确定的降级行为，不留下损坏的输出；
- 约定所引入的数据文件由仓库作者书写，属不可信输入，渲染时按纯文本转义处理，URL 需限定 scheme 白名单；
- 首个适用该 ADR 的特性是术语标注与解释（[spec 017](../specs/017-glossary-terms.md)）。
