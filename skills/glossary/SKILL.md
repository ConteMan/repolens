# repolens 术语标注与解释

帮助用户在**他自己的文档仓库**里建立术语标注，产出符合 repolens 规范的文件，使构建出的站点中被标注的词可以原地展开解释。

## 前提

- 目标仓库是一个用 repolens 构建站点的 Git 仓库；
- 你能读写该仓库的文件；
- 能执行命令时可用 `repolens build` 验证结果，不能执行时按本文末尾的自查清单人工核对。

## 边界

1. **范围由用户给定。** 只处理用户明确指定的文件、目录或术语清单，不扩大到整个仓库。
2. **不自动识别术语。** 不扫描正文按词频或词表自行决定标注对象。可以基于阅读提出候选并说明理由，但是否标注由用户决定。
3. **不改写正文表述。** 插入标注不得改变原有文字、语序和标点，只在词的两侧加链接语法。
4. **不确定就问。** 术语的准确含义、归属平台、易混点，凡是无法从仓库内容确证的，向用户提问而不是猜测后写入。写错的解释比没有解释更有害。

## 工作流

### 1. 确认范围与读者

先问清两件事，它们决定后续所有判断：

- **范围**：哪些文件或目录；
- **读者**：这份文档写给谁看。读者画像直接决定标注密度——给产品经理看的投放文档和给 SRE 看的运维手册，需要解释的词几乎没有交集。

用户已经给出术语清单时，仍要确认读者，用来判断清单里的词是否都值得标、以及解释该写到什么深度。

### 2. 盘点现有术语库

**在新建任何条目之前**，先列出 `<glossary.dir>`（默认 `.repolens/glossary/`）下已有的条目，以及仓库中已经使用的标注。

这一步是防止术语库劣化的关键：跳过它，仓库里就会同时出现 `mediation` 和 `ad-mediation` 两个含义重叠的 key。对每个待处理的术语：

- 已有含义相同的条目 → 复用其 key，不新建；
- 已有条目含义接近但确实不同 → 可以新建，但必须在两条的 `warning` 中互相说明差异；
- 没有 → 新建。

### 3. 与用户确认术语清单

把待标注术语整理成清单，逐条与用户确认。清单里每条给出：key、规范名、一句话解释、以及**为什么值得标注**。

值得标注的信号，按优先级：

1. **同名不同义**——同一个词在不同平台或语境下指不同的东西。这类词最值得标，`warning` 字段通常写得出内容；
2. 对目标读者构成理解障碍的行业概念；
3. 本文档中含义被收窄或特化的通用词。

不值得标注的：

- 解释不比字面意思多出信息的词；
- 目标读者的日常用语；
- 只出现一次且当场已用一句话解释清楚的词。

### 4. 编写术语库条目

每个术语一个文件：`<glossary.dir>/<key>.yml`，**文件名即 key**，文件内不写 key 字段。

```yaml
title: 广告聚合
alias: Ad mediation
summary: 行业通用能力：在多个广告源之间统一请求、竞价或瀑布选择，以提高填充率和收益。常见实现有 AppLovin MAX 与 Google AdMob 中介。
warning: AdMob 既可能是 MAX 内的一个广告源，也可能自己作为主聚合平台。先确认它当前扮演哪种角色，再配置收入入口。
source:
  label: AppLovin MAX 官方说明
  url: https://developers.applovin.com/en/max/getting-started/
```

字段规则：

| 字段 | 必填 | 写法 |
|---|---|---|
| `title` | 是 | 规范名。正文里怎么写不影响它 |
| `alias` | 否 | 别名、外文名、常见缩写 |
| `summary` | 否 | 脱离本文也成立的通用解释。一到三句。必要时在句中点明归属——是行业通用概念，还是某个平台/服务的私有实现 |
| `warning` | 否 | 易混点与常见误用。能写出内容说明这个术语值得标 |
| `source` | 否 | `{label, url}`，权威出处。URL 仅限 http/https |
| `page` | 否 | **只写在文档 front matter 里**，不写在术语库文件中 |

所有字段是**纯文本**：不解析 Markdown、不允许内嵌 HTML，写 `**粗体**` 只会原样显示。需要提及字段名或代码标识符时直接写，不加反引号。单字段不超过 2000 字符。

`summary` 与 `page` 的分工是这套格式的核心，不要混：

- `summary` 回答"这个词是什么"——换一个仓库、换一篇文档仍然成立；
- `page` 回答"在这篇文档里它具体指什么"——通常是收窄、特化或点明本文的口径。

### 5. 写文档语境（可选）

某个术语在特定文档里有更具体的含义时，在该文档的 front matter 中补充：

```yaml
---
title: 投放归因与广告收入数据流
glossary:
  mediation:
    page: 主聚合平台决定展示哪家广告源的广告，并形成展示与收入事实；它不负责判断最初是哪个买量渠道带来了用户。
---
```

同一段落还可以定义**只在本文档可见的私有术语**：写法相同，给出 `title` 等字段即可，不必在公共术语库建文件。适用于一次性的、不会在其他文档复用的词。

front matter 中的字段整体覆盖公共库的同名字段（`source` 作为整体替换），未写的字段沿用公共库。

### 6. 在正文插入标注

标注语法是标准 Markdown 链接，目标为 `term:` 加 key：

```markdown
[广告聚合](term:mediation)与变现平台拥有展示级收入事实。
```

显示文本与 key 解耦：正文写"渠道""Channel""媒体源"都可以指向同一个 key，用哪个词由行文决定，不必迁就 key 或 `title`。

**密度规则**——过度标注比漏标更伤可读性，满屏虚线会让读者不知道该点哪个：

- 每个术语在**每个小节内只标注首次出现**，同一段落绝不标两次；
- 一屏正文里的标注控制在三个以内，超出说明要么该精简清单，要么该在正文里直接解释；
- 标题、代码块、表格表头内不标注；
- 已经在紧邻上下文中解释过的词不再标注。

### 7. 开启配置

**这一步不能省。**特性默认关闭，标注写完但配置没开，构建出的站点不会有任何变化——这是最常见的失败方式。

在仓库根的 `.repolens.yml` 中：

```yaml
render:
  markdown:
    glossary: true
glossary:
  dir: .repolens/glossary
  strict: true
```

只有部分目录需要术语功能时，用规则级联而不是全局开启：

```yaml
rules:
  - match: "docs/**/*.md"
    markdown: { glossary: true }
```

`.repolens.yml` 已存在时合并进去，不要覆盖用户已有的配置段。

### 8. 验证

能执行命令时：

```sh
repolens build . -o /tmp/repolens-check
```

`strict: true` 下引用了未定义的术语会直接构建失败，并给出文件、行号与 key。构建通过后确认渲染结果：浏览页正文末尾应出现术语表小节，被标注的词是指向该小节的链接。

不能执行命令时，按下面的清单逐项核对。

## 自查清单

- [ ] 每个 `term:` 引用都有对应的术语库文件或 front matter 定义；
- [ ] 每个术语库文件名符合 `^[a-z0-9]([a-z0-9-]*[a-z0-9])?$`，且文件内没有 key 字段；
- [ ] 没有语义重复的 key；
- [ ] 所有条目都有 `title`；
- [ ] 字段内没有 Markdown 标记或 HTML；
- [ ] `source.url` 都是 http/https；
- [ ] `page` 只出现在文档 front matter，没有写进术语库文件；
- [ ] 正文文字未被改动，只增加了链接语法；
- [ ] 没有小节内重复标注；
- [ ] `.repolens.yml` 已开启 `render.markdown.glossary`。

## key 命名

合法性要求是 `^[a-z0-9]([a-z0-9-]*[a-z0-9])?$`（小写字母、数字、连字符，不以连字符开头或结尾）。在此之上：

- **用概念名，不用显示文本的音译**：`mediation` 而不是 `guanggao-juhe`；
- **缩写全小写**：`mmp`、`ilrd`、`s2s`，不写 `MMP`；
- **不加平台前缀**，除非该概念确实是某平台私有：`mediation` 是通用概念，`applovin-max` 是具体产品，两者都成立且不同；
- **用单数、用名词**：`campaign` 而不是 `campaigns`；
- key 一旦被引用就**不要改名**——改名要同步修改所有引用处，收益通常不值得。宁可保留一个不够漂亮的 key。

## 增量维护

初次建立之后，长期形态是零散追加：写新文档时顺手加一两个术语。这条路径上必须做的仍然是第 2 步——**先盘点，再新建**。

其他增量场景：

- **术语含义变了**：直接改术语库文件，所有引用处自动跟随，不需要动正文；
- **两条术语其实是一回事**：保留一条，把另一条的引用改成保留的 key，删除多余文件；
- **删除术语**：先确认没有引用，否则 `strict` 模式下构建会失败；
- **术语库存在但从未被引用**：属于无害的冗余，可保留待用，也可清理。

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 标注写完没开配置 | 站点毫无变化，用户以为功能坏了 | 第 7 步 |
| 不盘点就新建 key | 术语库出现语义重复条目 | 第 2 步 |
| `page` 写进术语库文件 | 本文语境的解释污染了所有引用该术语的文档 | `page` 只写在 front matter |
| 字段里写 Markdown | 原样显示为字面字符 | 纯文本 |
| 把所有专有名词都标上 | 满屏虚线，可读性下降 | 密度规则 |
| 猜测术语含义后写入 | 错误解释比没有解释更有害 | 向用户提问 |
| 为了标注改写正文 | 破坏作者的表述 | 只加链接语法 |
